# Разбиения и протокол оценки

Этап 6, 25 ноября 2026 года. Пользователь согласовал F1 как основной показатель. Полнота атак, доля ложных тревог, precision, матрицы ошибок и число примеров приводятся рядом. Настройка моделей и промптов использует внутреннюю валидацию; итоговые показатели рассчитываются на внешних проверочных частях.

## Данные и задачи

| Корпус | Наблюдения | Эталон | Основная схема |
|---|---:|---|---|
| NIRS после удаления одной пустой строки | 32 529 | Пять исходных классов | 5 внешних групповых фолдов, по 3 внутренних |
| SQLStateGuard | 161 022 | Бинарные метки авторского релиза | Перенос web_app → WordPress и обратно; по 3 внутренних фолда |
| Контролируемые сценарии | 1 200 | Бинарные метки сценария и политики | 3 внешних групповых фолда, по 2 внутренних |

Для бинарных задач основной показатель — F1 положительного класса 1. Для исторической пяти-классовой задачи — macro-F1 по фиксированным классам 0–4. У NIRS вторичные полнота атак и FPR вычисляются после сведения исходных меток 1–4 к тревоге. Качество классификации типа угрозы и качество бинарной тревоги показываются раздельно.

Уникальное хранимое наблюдение имеет единичный вес в основном расчёте. Для SQLStateGuard дополнительно допускается расчёт с исходной кратностью вхождений. Направления переноса и корпуса оцениваются отдельно. Основной результат групповой CV — F1 по объединённым внешним прогнозам, дополненный результатами и поддержкой каждого фолда.

## Определение групп

Группы построены одновременно для трёх зафиксированных версий данных. Учитываются точный текст, варианты по краевым пробелам, лексический шаблон с маскированием литералов, известные сценарии, шаблоны генерации и связи родитель–вариант. В старом NIRS связанные партии генерации определяются по источнику диалект/сложность и исходному классовому промпту. Эти поля являются метаданными разбиения.

Для новых контролируемых вариантов перед определением лексического шаблона восстанавливается исходная операция. Это сохраняет связи с родителем и различает полезную нагрузку одинаковых динамических обёрток. Имена объектов остаются в шаблоне; произвольное семантическое тождество SQL по нему не утверждается.

Всего учтены 194 751 наблюдение и 86 837 глобальных компонент. В пределах NIRS представлены 25 347 компонент, SQLStateGuard — 61 508, контролируемого набора — 7. Компоненты могут объединять записи разных корпусов, поэтому числа по корпусам не складываются в глобальное число.

Каждый основной фолд проверяется на отсутствие пересечений компонент, точного SQL и применяемых лексических шаблонов между train, validation и test. У контролируемого набора также проверяется наличие повышения привилегий и эксфильтрации в каждой используемой части.

Фиксированный seed — 20261125. Группы распределяются по классам и размерам без использования результатов моделей. Для небольшого числа компонент перебираются допустимые распределения; для больших наборов применяется детерминированное жадное распределение. При одинаковом балансе классов учитывается размер частей. Подмена групп строками при недостатке независимых примеров не производится.

## Обучение, настройка и внешняя проверка

Во внешнем фолде выделены train и test. Только train становится областью внутренних фолдов, где выделяются train и validation. Подбор представления, регуляризации, порога и других параметров использует внутренние результаты. Затем выбранная конфигурация обучается на всей внешней train-части и оценивается на соответствующем test.

Для контролируемого корпуса размеры внешних test-частей — 480, 360 и 360; train — 720, 840 и 840. Для NIRS test-части содержат 6 579, 6 266, 6 899, 6 318 и 6 467 строк. Внешние проверочные фолды покрывают каждое наблюдение своего корпуса по одному разу.

Внутренние разбиения ссылаются на идентификатор родительского внешнего разбиения, номер фолда и часть train. Хранилище запрещает включать в них другие наблюдения. Словарь, статистики признаков, отбор признаков и обучаемые преобразования строятся только на соответствующей обучающей части.

Порог выбирается по F1 внутренней валидации. При равном F1 последовательно учитываются меньший FPR, большая полнота и более простая конфигурация. Жёсткий эксплуатационный лимит FPR не вводился; это отдельный публикуемый показатель.

Для сравнения запоминания подготовлен дополнительный пяти-фолдовый строковый контроль на том же NIRS из 32 529 строк. Его пересечения групп посчитаны и сохранены. Он имеет роль diagnostic_random_control и не заменяет основную групповую оценку. Исторические разбиения этапа 1 сохранены отдельно.

## Перенос между приложениями

При web_app → WordPress обучение использует 92 632 наблюдения web_app, проверка — все 68 390 наблюдений WordPress. В обратном направлении роли приложений меняются. Валидация формируется групповыми фолдами только внутри исходного приложения.

Правило исключения задано заранее: если глобальная компонента присутствует в целевом приложении, её строки из исходного приложения исключаются из обучения; целевое приложение сохраняется целиком. В выбранной версии общих компонент между этими двумя приложениями не обнаружено, поэтому исключений здесь нет. Перекрытия с NIRS отражены в group_audit.json и учитываются глобальной картой групп.

Аудит пересечений считает уникальные подписи. Например, у NIRS и WordPress общим оказался один уникальный текст SQL; в отчёте этапа 4 ему соответствовали 345 исходных вхождений. Кратность вхождений и число уникальных текстов имеют разные единицы учёта.

SQLStateGuard ранее изучался в ревью и остаётся известным контролем переноса. Для будущей оценки на новом внешнем источнике сначала фиксируются код, признаки, модели, пороги, промпты и критерии выбора источника; затем фиксируются версия данных и состав проверки.

## Общая проверка ML, правил и LLM

Сохранён упорядоченный пул из 68 870 проверочных наблюдений: WordPress из направления web_app → WordPress и test фолда 0 контролируемого набора. Внутри каждой комбинации задачи и метки порядок определяется фиксированным хешем идентификатора. Объём основного LLM-прогона выбирается после оценки стоимости пилота; квоты выбирают префиксы этого порядка до получения основных ответов.

Все методы в парном сравнении оцениваются на одних идентификаторах и в одном порядке. Показатели ML на полном внешнем наборе и показатели на общей подвыборке подписываются отдельно. Для контролируемых сценариев SQL-only и SQL+context используют одни наблюдения. Контекстный срез одинаковых текстов SQL с разными политиками сохраняется в оценке и показывается отдельно.

Для разработки LLM выделены 30 наблюдений внутренней validation: по пять штатных и пять атак для SQLi, повышения привилегий и эксфильтрации. Шесть кандидатов few-shot — по одному на каждую такую комбинацию — выбраны из соответствующей внутренней train-части. Их группы не пересекаются друг с другом и с итоговым общим пулом. Пилот имеет назначение development_only_not_final_test.

Ошибка API или разбора ответа сохраняет отдельный статус. Она не превращается в legit. Основной F1 для ранжирования требует решений по всем запланированным примерам. При неполном покрытии отдельно приводятся покрытие, статусы ошибок и условные метрики по успешным решениям. Неопределённая доля, например FPR при отсутствии штатных примеров, сохраняется как null.

## Сохранение и использование

Созданы 15 актуальных конфигураций: две внешние групповые CV, восемь внутренних CV, строковый диагностический контроль и два направления переноса с двумя внутренними CV. Идентификаторы и состав находятся в [split_registry.json](../results/stage6/split_registry.json). Выбирать конфигурацию следует по этому реестру и split_id.

Состав хранится в nirs.split_members и в сжатых манифестах идентификаторов. Файлы gzip воспроизводимы: имя файла и текущее время не входят в заголовок. Карта групп сохранена в nirs.sample_groups/nirs.group_members и [groups.jsonl.gz](../results/stage6/groups.jsonl.gz). Формат memberships: один id и строка roles по fold_order; T — train, V — validation, E — test, X — excluded.

Миграция 004 добавляет печати nirs.split_seals. Они фиксируют контрольные суммы конфигурации и состава, включая исторические разбиения. После фиксации изменение, добавление и удаление назначений запрещены. Новая конфигурация получает новый идентификатор. Внутренние области проверяются по зафиксированной родительской train-части.

```powershell
.\.venv\Scripts\python.exe -B src/manage_storage.py migrate
.\.venv\Scripts\python.exe -B src/prepare_splits.py
$env:NIRS_RUN_DB_TESTS='1'
.\.venv\Scripts\python.exe -B -m unittest discover -s tests -v
```

Пример получения упорядоченных идентификаторов для последующих этапов:

```python
import json
from pathlib import Path
from storage import Storage

registry = json.loads(Path('results/stage6/split_registry.json').read_text())
split = registry['protocols']['controlled-outer']['split_id']
test_ids = Storage().split_ids(split, fold=0, part='test')
```

Контракт метрик реализован в [evaluation_metrics.py](../src/evaluation_metrics.py), машиночитаемая спецификация — [evaluation_specification.json](../results/stage6/evaluation_specification.json). Алгоритм группировки и проверки — [split_protocol.py](../src/split_protocol.py), сборка и фиксация — [prepare_splits.py](../src/prepare_splits.py).

Методологические опоры: [групповые проверки sklearn](https://scikit-learn.org/stable/modules/cross_validation.html#cross-validation-iterators-for-grouped-data), [определения метрик sklearn](https://scikit-learn.org/stable/modules/model_evaluation.html#f1-score), [хеш-функции PostgreSQL](https://www.postgresql.org/docs/17/functions-binarystring.html). На этом этапе сформирован протокол эксперимента; обучение представлений и моделей относится к следующим этапам.
