# Модели и регулярные выражения — этап 8

Дата: 25 ноября 2026 года. Исходная ревизия: `74347a3`. Пользователь согласовал настройку трёх опорных задач сейчас; остальные внешние фолды и обратное направление переноса относятся к этапу 10.

Этап реализует загрузку данных и разбиений из PostgreSQL, подбор параметров на внутренних групповых фолдах, обучение окончательных train-моделей, сохранение полных пайплайнов и версионированные контроли правилами. Сводные числа этого этапа являются результатами разработки на validation; они не заменяют внешнюю оценку.

Загрузчик `load_inputs` получает только ID родительской train-части запечатанного разбиения. В каждом внутреннем фолде train и validation полностью покрывают эту область и не пересекаются. Словарь, IDF, масштабирование и отбор признаков обучаются заново на train фолда. Test-строки не загружаются этим ML-процессом. Для контролируемых сценариев SQL-only и SQL+context используют одинаковые ID и метки.

NIRS сохраняет пяти-классовую постановку как исторический контроль; исходные метки не объявляются новым проверенным бинарным эталоном. Бинарная тревога старого контроля определяется явно: любой класс 1–4 означает тревогу. Новые бинарные ML-модели обучаются на SQLStateGuard и контролируемом корпусе, с раздельными результатами.

## Зафиксированный поиск

До запусков сохранены `results/stage8/search_plan.json`, версии библиотек, seed 20261125, контрольные суммы исходного кода и миграций. Расширение поиска по результату внешнего test не предусмотрено.

Для Logistic Regression и LinearSVC сравниваются три профиля:

- `C=0.05`, `class_weight=balanced`;
- `C=1`, `class_weight=balanced`;
- `C=1`, без весов классов.

Logistic Regression использует `liblinear`, до 4 000 итераций; LinearSVC — `dual=auto`, до 10 000. Предупреждение о несходимости останавливает выбор вместо сохранения такого кандидата как успешно настроенного.

RandomForest использует 100 деревьев и три профиля: глубина 12 / минимум 3 объекта в листе / balanced; неограниченная глубина / минимум 1 / balanced; неограниченная глубина / минимум 3 / без весов. Все модели получают независимые экземпляры классификатора и сохранённого пайплайна. Один вычислительный поток фиксирует воспроизводимый режим и ограничивает нагрузку.

SQL-ветки: исходный текст со словарями до 10 000 и 50 000, маскированный текст, маскированный текст со структурой и отбором до 1 000 признаков. Для NIRS дополнительно есть историческая текстовая нормализация. Для малого контролируемого набора оставлен один исходный текстовый предел 10 000, поскольку фактический словарь меньше обоих пределов. Контекстные варианты: текст и контекст; все блоки с отношениями политики; структура и контекст с отношениями политики. Детали преобразований описаны в [features.md](features.md).

Одинаковая конфигурация проходит все внутренние фолды задачи. Её прогнозы объединяются так, чтобы каждому наблюдению внешней train-области соответствовал ровно один прогноз модели, не обучавшейся на этом наблюдении. Для бинарной задачи общий порог выбирается по F1 этих объединённых validation-прогнозов. Равные оценки переходят порог вместе; проверяются все различные оценки и вариант без тревог. Для линейных моделей используются значения `decision_function`, для леса — вероятность класса 1. Эти шкалы не смешиваются между разными методами.

Основной порядок выбора: выше F1, ниже FPR, выше полнота атак. Далее используется фиксированный порядок сложности: меньше средняя фактическая ширина матрицы, меньше C, меньше глубина леса, больше минимум объектов в листе, затем стабильное описание конфигурации. Для пяти классов используется обычный выбор класса и macro-F1; бинарный порог к такой модели не применяется. Отдельного жёсткого ограничения FPR пользователь не вводил.

После выбора параметров преобразователь и классификатор заново обучаются на всей соответствующей внешней train-части. Найденный внутренний порог сохраняется вместе с полной моделью `FrozenDecisionModel`. Внешние результаты не участвуют в этом обучении.

## Контроли правилами

`regex_v1` сохраняет исходные правила `RegexDetector` и их порядок. В NIRS остаются исходные пять выходных классов; для бинарных задач ненулевой выход сводится к тревоге. Исправления не подменяют этот контроль.

`regex_v2` — отдельная бинарная версия эвристик. Обычные комментарии, конкатенация и кодирование сами по себе больше не означают атаку. Содержимое строк не вызывает правило по одному лишь упоминанию опасного ключевого слова. Сохранены явные признаки чувствительных операций, экспорта, некоторых SQLi и связанных опасных конструкций. Это эвристический SQL-only контроль: разрешённый `GRANT` или штатный `UNION` всё ещё может дать ложную тревогу. Улучшение относительно исходной версии должно подтверждаться метриками конкретного корпуса.

`policy_only` — ограниченная самостоятельная проверка явно заданной политики по SQL и доступному до решения контексту. Она распознаёт базовые выдачи прав, членство в роли и плоский SELECT с tenant-фильтром, включая поддержанные агрегаты и назначение экспорта. Модуль не импортирует генератор, каталог сценариев, функцию разметки, родительский SQL или ожидаемую операцию. Сложные вложенные запросы, вызовы процедур, динамические тела и неподдержанные выражения получают отказ от решения.

Политика должна иметь полное покрытие объявленной области; операция должна попадать в неё и однозначно соответствовать явному allow или deny. Неизвестное условие, противоречие, неполный контекст или неподдержанный SQL не превращаются в «штатный». Такие случаи хранятся со статусом `not_run` и причиной. Поэтому для policy-only показываются покрытие и условные метрики; при неполном покрытии основной F1 отсутствует.

`regex_policy` применяет поддержанную проверку политики и иначе использует `regex_v2`. Явный allow может снять тревогу по допустимой выдаче прав; явный deny может выявить нарушение без характерных SQLi-конструкций. Проверка политики и ML получают один и тот же разрешённый контекст.

При технической проверке фиксированного модуля политики было просмотрено агрегированное согласие с разметкой всего известного контролируемого корпуса: 554 поддержанных решения из 1 200, все 554 совпали с аннотациями; 646 операций не поддержаны. Это включает строки, назначенные во внешние test-части. После этой проверки правила не изменялись; она не использовалась для настройки ML или порогов. Последующая оценка данного контроля на этом же корпусе не считается слепой. Диагностика и её назначение отдельно сохранены в `rule_conformance_check.json`. Результат показывает согласованность узкого механизма с известной политикой, а не качество универсального SQL-детектора.

## Хранение, проверки и продолжение

Каждая матрица CSR float32 зарегистрирована в `nirs.representations`, связана с версией датасета, train-разбиением, фолдом, порядком ID строк и столбцов, обученным преобразователем и исходным кодом. Разные классификаторы могут использовать одинаковую уже обученную матрицу одного фолда; пайплайны содержат независимые экземпляры состояния.

Для каждого испытанного кандидата сохранены полный внутренний пайплайн, исходные validation-оценки до выбора порога, метки, параметры, предупреждения и контрольные суммы. Все кандидаты выбранного метода и режима входа связаны с итоговым запуском через реестр артефактов. Основные построчные прогнозы выбранных моделей и правил хранятся в `nirs.predictions`, метрики — в `nirs.metrics`, полные train-модели — в `nirs.run_artifacts`. Матрицы и модели находятся в локальном реестре и `.local/stage8/`; компактные отчёты публикуются в Git.

Миграция 005 разрешает `inner_validation` только для явно объявленного запуска разработки, связанного с конкретным split_id. База проверяет принадлежность к настоящей validation-части и соответствие эталона закреплённой аннотации. Существующий контроль принадлежности к test для исторических и внешних прогнозов сохранён. Ошибочная подмена validation назначением test отклоняется.

Повторный запуск сверяет конфигурации и суммы файлов и продолжает работу из кэша. Сохранённые классификаторы проверяются по точному совпадению оценок после загрузки; для выбранных полных пайплайнов повторяется преобразование всей внутренней validation-части и сравниваются оценки. Для окончательных train-моделей проверяется повторная загрузка без обучения. Отдельный аудит пересчитывает метрики из строк PostgreSQL, реконструирует результаты всех кандидатов по архивам фолдов и проверяет правило выбора.

```powershell
.\.venv\Scripts\python.exe -B src/baseline.py --plan-only
.\.venv\Scripts\python.exe -B src/baseline.py
.\.venv\Scripts\python.exe -B src/audit_model_runs.py
$env:NIRS_RUN_DB_TESTS='1'
.\.venv\Scripts\python.exe -B -m unittest discover -s tests -v
```

По умолчанию запускаются согласованные три опорные области. `--scope NAME` позволяет продолжить отдельную область, `--all-scopes` запускает все сохранённые внутренние протоколы. Для следующих внешних фолдов параметры и признаки должны подбираться внутри их собственных train-областей; перенос выбранного здесь победителя как будто он выбран независимо для другого фолда недопустим. Историческая CSV-процедура доступна отдельно как `baseline.historical_main`; старый контроль воспроизводится через `reproduce_baseline.py`.

Основания реализации: [LinearSVC в sklearn 1.5](https://scikit-learn.org/1.5/modules/generated/sklearn.svm.LinearSVC.html), [RandomForestClassifier](https://scikit-learn.org/1.5/modules/generated/sklearn.ensemble.RandomForestClassifier.html), [метрики классификации](https://scikit-learn.org/1.5/modules/model_evaluation.html#precision-recall-f-measure-metrics).
