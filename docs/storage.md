# PostgreSQL и артефакты

Хранилище этапа 3: PostgreSQL 17.12 в Docker, клиент Psycopg 3.3.9,
Windows x64 / CPython 3.12.4. В `compose.yaml` закреплён digest официального образа.
Порт опубликован на `127.0.0.1:55432`. Данные сервера находятся в постоянном
Docker-томе `nirs-sql_nirs_pgdata`.

## Запуск

Из корня проекта:

```powershell
python -m venv .venv --system-site-packages
.\.venv\Scripts\python.exe -m pip install -r requirements-lock.txt
python -B src/init_storage.py
docker desktop start --detach
docker compose --env-file .env.db.local up -d --wait postgres
.\.venv\Scripts\python.exe -B src/manage_storage.py migrate
```

На текущем компьютере окружение наследует уже установленные библиотеки ML.
Для полностью отдельного окружения создайте venv без `--system-site-packages`
и установите тот же lock. Полная новая установка всех 134 пакетов не проверялась;
реальные интеграционные тесты выполнены в созданном окружении проекта.
С pip 24 на данном Windows для установки Psycopg потребовался параметр
`--use-feature=truststore`, использующий системные корневые сертификаты;
проверка TLS не отключалась.

`init_storage.py` создаёт `.env.db.local` со случайным паролем и сохраняет
существующий файл. Он отделён от `.env` с API-ключами. В Git включён только
пример `.env.db.example`. Подключение Python настраивается `NIRS_DB_HOST`,
`NIRS_DB_PORT`, `NIRS_DB_NAME`, `NIRS_DB_USER`, `NIRS_DB_PASSWORD`.
Переменные процесса имеют приоритет над локальным файлом.
`NIRS_ARTIFACT_ROOT` задаёт каталог файлов, по умолчанию `.local/artifacts`.

Для остановки: `docker compose --env-file .env.db.local stop postgres`.
Следующий `up -d --wait` использует существующий том.

## Схема и ограничения

В схеме `nirs` находятся 22 таблицы, включая журнал миграций.

| Сущности | Назначение |
|---|---|
| sources, source_versions | Источники, байтовые и LF-хеши, исходные колонки, число принятых и отклонённых строк |
| import_jobs, rejected_records | Попытки импорта, причины ошибок и сохранённые отклонённые строки |
| observations, occurrences | Неизменённый SQL, контекст, исходные вхождения, метки и исходные поля |
| annotations | Версии проверенной разметки с основанием; исходная метка хранится отдельно |
| dataset_versions, dataset_members | Зафиксированный состав и конкретные ревизии аннотаций |
| sample_groups, group_members | Связанные сценарии, шаблоны и кампании |
| splits, split_members | Разбиения и принадлежность наблюдений фолдам |
| artifacts, source_artifacts | Файлы по контрольным суммам и связи с источниками |
| representations, representation_artifacts | Конфигурации представлений, матрицы и метаданные строк/столбцов |
| experiment_runs, predictions, metrics, run_artifacts | Конфигурации, построчные ответы, показатели и файлы запусков |

Миграции применяются в транзакции и проверяются по SHA-256 после CRLF → LF.
Изменение уже применённой миграции останавливает запуск. Следующее изменение
схемы оформляется новым SQL-файлом.

SQL-примеры передаются параметрами или через COPY как значения полей и не
исполняются. Вставка строк содержит фиксированный SQL приложения; динамические
имена служебных таблиц экранируются через `psycopg.sql.Identifier`.

Наблюдения сохраняются по исходным вхождениям; совпадающие тексты индексируются
по `sql_sha256` и не объединяются автоматически. Противоречащие исходные метки
сохраняются у соответствующих вхождений. Повторный импорт одной версии файла
использует те же идентификаторы и не добавляет копии наблюдений.

У старых CSV `unit_kind=unknown`, контекст неизвестен, аннотация needs_review,
целевая метка null. Это начальное состояние до аудита этапа 4. Числа и значения
исходных label/label_name сохранены в occurrences. Старые файлы не меняются.

Фиксированный датасет ссылается на конкретную annotation_id. Новая аннотация
добавляется через `Storage.append_annotation`; старые ревизии и состав frozen
датасета защищены триггерами. Изменение текста, контекста или вида SQL создаёт
новое наблюдение для новой версии данных, с сохранением связей происхождения.

Предсказания имеют FK к датасету и тестовому разбиению. Для binary значение
true_label проверяется по закреплённой аннотации. Для исторических запусков
legacy_five_class эталон берётся из исходной пяти­классовой метки вхождения.
Необработанный ответ хранится с отдельным статусом и predicted_label=null.

Проверки содержательной разметки и группового разделения относятся к этапам 4
и 6. Сейчас перенесён исторический контроль с прежним разбиением по строкам.

## Импорт

```powershell
.\.venv\Scripts\python.exe -B src/manage_storage.py import-csv data/processed/dataset.csv --dataset-name legacy-nirs-stage1
.\.venv\Scripts\python.exe -B src/manage_storage.py import-csv data/processed/generated.csv
.\.venv\Scripts\python.exe -B src/manage_storage.py import-csv data/raw/real_payloads.csv
.\.venv\Scripts\python.exe -B src/manage_storage.py import-csv data/raw/sqli_dataset.csv
```

Команда с `--dataset-name` выводит dataset_version_id. Для текущего эксперимента
он также записан в `results/stage3/import_report.json`.
Итог: 65 093 вхождения четырёх файлов; в версии основного корпуса — 32 530.
Исходные файлы не объединяются в одну обучающую выборку. SQL и все исходные поля
проверены обратным сравнением с CSV для каждого вхождения.

Импорт идёт пакетами в общей транзакции. Внутренняя ошибка откатывает частично
записанные пакеты, а попытка отмечается failed. Ошибки числа колонок и NUL
сохраняются в rejected_records с причиной и исходными данными; в реальных четырёх
CSV таких отклонений не было. CSV-ошибка декодирования или структуры останавливает
импорт файла целиком. Пустые и пробельные значения сохраняются для аудита.

Перенос архивов этапа 1 с указанным dataset_version_id:

```powershell
.\.venv\Scripts\python.exe -B src/manage_storage.py import-stage1 results/runs/stage1-control --dataset <dataset_version_id> --name stage1-control
.\.venv\Scripts\python.exe -B src/manage_storage.py import-stage1 results/runs/stage1-repeat --dataset <dataset_version_id> --name stage1-repeat
```

Нужны полные локальные архивы, включая модели, либо их повторное создание из
кода этапа 1. Опубликованный `results/stage1/` является подмножеством архивов.
В БД зарегистрированы 8 запусков методов и 312 288 прогнозов. Модели связаны
с соответствующим методом; Regex не получает обученную модель.
`Storage.dataset_records` возвращает записи контракта, закреплённые в выбранной
версии. Перевод обучающих скриптов на эти выборки предусмотрен следующими этапами.

## Файлы артефактов

Реестр сохраняет относительный путь, размер, SHA-256 и статус pending/ready/missing.
Сначала создаётся pending-запись, затем файл копируется в каталог с адресом по
содержимому, проверяется и атомарно переименовывается. После этого статус становится
ready. Неудачная запись остаётся pending; повторная регистрация проверенного
исходного файла позволяет завершить её. `Storage.get_artifact` проверяет готовность,
наличие и контрольную сумму перед использованием.

Проверка доступности файлов:

```powershell
.\.venv\Scripts\python.exe -B src/manage_storage.py check-artifacts
```

В текущем реестре 43 уникальных файла: исходные CSV и артефакты этапа 1.
Матрицы нового исследовательского представления будут строиться на этапе 7;
сохранение `.npz` и его связи с идентификаторами строк проверено на маленькой
тестовой матрице в отдельной БД.

## Резервное копирование и восстановление

```powershell
.\.venv\Scripts\python.exe -B src/manage_storage.py backup .local/backups/my-backup
.\.venv\Scripts\python.exe -B src/manage_storage.py restore-check .local/backups/my-backup --artifact-root .local/restore-validation/my-backup
```

Каталоги назначения должны быть новыми. Backup создаёт custom-дамп pg_dump,
копии всех ready-файлов и общий manifest.json с хешами и отпечатками таблиц.
Все записи через Storage используют единый advisory-lock. Backup удерживает
его до окончания дампа и копирования файлов; незавершённые артефакты остаются
непригодными для использования. Прямые сторонние записи в БД и ручное изменение
файлов обходят этот протокол и должны быть остановлены на время копирования.

restore-check создаёт новую БД со случайным именем nirs_restore_*, восстанавливает
дамп, переносит файлы в отдельный корень, сравнивает все таблицы и хеши, затем
проверяет прогнозы сохранённых исторических ML-пайплайнов. Временная БД удаляется
в finally; исходная не перезаписывается. Файлы проверки остаются в указанном
каталоге. Работа выполняется с собственными доверенными дампами и joblib-файлами.

Проверка текущего снимка прошла: 22 таблицы, 43 файла, 6 holdout-пайплайнов.
Отчёт: `results/stage3/restore_report.json`. Сам дамп, файлы объектов и пароль
остаются локально; для переноса резервной копии нужен весь каталог backup,
а для воспроизведения проекта — исходники, зависимости и исходные данные.

## Тесты

```powershell
$env:NIRS_RUN_DB_TESTS = '1'
.\.venv\Scripts\python.exe -B -m unittest discover -s tests -v
```

35 тестов: 20 предыдущих и 15 интеграционных проверок хранилища.
Интеграционные проверки создают отдельную временную БД и удаляют её после работы.
Без флага они явно пропускаются. Реальная проверка pg_dump/pg_restore выполняется
отдельной командой и отражается в restore_report.json.

Артефакт-манифесты предыдущих этапов относятся к версиям файлов в соответствующих
коммитах Git; последующие изменения общих requirements не переписывают историю.

Официальные основания: [образ PostgreSQL](https://hub.docker.com/_/postgres),
[параметры Psycopg](https://www.psycopg.org/psycopg3/docs/basic/params.html),
[pg_dump](https://www.postgresql.org/docs/17/app-pgdump.html),
[pg_restore](https://www.postgresql.org/docs/17/app-pgrestore.html).
