# Контракт исследовательских данных v1

Версия 1.0.0, 24 ноября 2026 года. Для этой работы согласовано включение
подтверждённого несанкционированного чтения чувствительных данных в эксфильтрацию,
даже если SQL не содержит явного экспорта или внешней передачи. Каналы различаются
отдельными тегами. Это операциональное определение исследования.

Машиночитаемая структура: `schemas/observation-v1.schema.json`.
Межполевые ограничения и формирование входа детектора: `src/data_contract.py`.
Инструкция разметки: `docs/annotation_guidelines.md`.
Учебные примеры: `tests/fixtures/contract_examples.json`.

## Единица наблюдения и идентичность

Наблюдение — неизменённый текст одного SQL-события и достоверный контекст,
доступный до решения детектора. SQL-событие может включать несколько операторов,
если именно этот текст передан как единый запрос. Исполнение SQL не требуется.

`observation_id` — постоянный непрозрачный идентификатор. Он не кодирует метку.
`source_id + source_version + source_record_id` идентифицируют исходное вхождение
для повторного импорта. Составные запросы и многострочный SQL не разрезаются
по переводам строк или точкам с запятой без отдельного основания.

Одинаковый SQL с разными контекстами — разные наблюдения. Изменение аннотации
создаёт новую ревизию, а не новый SQL. Точные повторы сохраняют происхождение
и кратность; группировка и объединение не выбирают произвольно первую метку.
Совпадение нормализованного текста не устанавливает семантическую идентичность.
Физические таблицы и ключи будут определены на этапе 3.

Версия датасета должна ссылаться на конкретную ревизию аннотации. Последующее
изменение current_annotation_id не изменяет уже зафиксированный датасет.

## Состав записи

| Поле | Назначение | Доступ детектору |
|---|---|---|
| `schema_version` | Версия структуры записи | Нет |
| `observation_id` | Идентификатор наблюдения | Нет |
| `sql.text` | Исходный текст без `strip`, декодирования или удаления комментариев | Да |
| `sql.unit_kind` | full_sql / payload_fragment / non_sql / unknown | Служебный отбор |
| `context` | Достоверные сведения до решения, с явной доступностью | Только разрешённая проекция |
| `source` | Источник, версия, вхождение, происхождение и исходная метка | Нет |
| `annotations` | История целевой разметки, основания и авторы | Нет |
| `current_annotation_id` | Ссылка на действующую ревизию | Нет |
| `grouping` | Связи сценариев, шаблонов, кампаний и преобразований | Нет |
| `execution` | Известный результат выполнения и его происхождение | Нет |

`source.origin`: public / controlled / llm_generated. Контролируемый сценарий
с SQL, предложенным LLM, имеет `origin=llm_generated` и ссылку на сценарий:
генерационное происхождение не теряется. `source.source_label` сохраняется как
получено, включая исходные числовые значения и текстовые названия.

`source.purpose=contract_fixture` обозначает учебный пример спецификации.
Такие записи не включаются в исследовательский train/test, независимо от метки.
Реальные записи получают `purpose=research` после предусмотренной проверки.

Полный реестр источников хранит URL, лицензию, версии, схемы импорта и хеши;
наблюдение ссылается на него через `source_id` и `source_version`.
Точный путь к исходному вхождению хранится в `source_record_id`, а хеш исходного
файла — в `source_file_sha256`. Неизвестный хеш допускается только как `null`
с ограничением в реестре источника; версия не заменяется текущим содержимым URL.

## Контекст

Каждое из пяти полей имеет оболочку:

```json
{
  "availability": "known",
  "value": "reporting_service",
  "evidence_ref": "scenario:permissions-v1",
  "available_before_decision": true
}
```

Для `unknown` или `not_applicable`: `value=null`, `evidence_ref=null`,
`available_before_decision=false`. Неизвестное и неприменимое — разные состояния.
`not_applicable` используется по описанному основанию, а не вместо пропуска.
Отсутствие сведений в публичном корпусе означает `unknown`.

| Поле контекста | Значение при known |
|---|---|
| `dialect` | mysql / postgresql / mssql / oracle |
| `active_role` | Действующая роль, а не роль, которую пытается получить запрос |
| `permissions` | Известные права на ресурсы, allow/deny, полнота сведений |
| `application_operation` | Идентификатор и описание текущей операции приложения |
| `policy` | Идентификатор, версия, правила операции и известные чувствительные ресурсы |

У прав есть `coverage=complete` или `partial`. Отсутствие разрешения в частичном
списке **не означает запрет**. Полный список относится только к указанным
`scope_resources`; вывод о других ресурсах по нему не делается. Явный deny
или исчерпывающий список в своей области может обосновывать запрет.
У политик также есть область и полнота. `allow` в этом формате не означает
отмену запрета другого уровня: права СУБД и политика операции проверяются отдельно.
Неописанные условия строк, колонок и динамических ролей не считаются известными.

Контекст берётся из метаданных источника или заранее заданного сценария,
а не из названия класса, текста ответа генератора или предсказания детектора.
После выполнения обнаруженная роль и результат кампании остаются свидетельствами
аннотации; они не подставляются задним числом в доступный модели контекст.
`evidence_ref` ссылается на проверяемое определение/метаданные и не выдаётся модели.

Наличие роли администратора, слова users, комментария или контекста само по себе
не определяет класс. В сценариях нужны штатные и вредоносные примеры с одинаковыми
ролями, операциями и схемами доступности полей.

## Целевая разметка и история

`target_label`: 0 — штатный, 1 — вредоносный, null — решения нет.
`status`: verified / needs_review / excluded. Только verified имеет бинарную
метку. needs_review и excluded не превращаются в отрицательные примеры.
excluded означает известное основание исключения из цели, а не повреждение записи.

У каждой аннотации есть идентификатор, последовательная ревизия, ссылка
`supersedes`, версия инструкции, объяснение, свидетельства, тип и идентификатор
автора проверки. Действующая аннотация — последняя в непрерывной истории.
Новая версия хранит основание изменения, а предыдущая не переписывается.

`threat_tags` допускает несколько значений: sqli, privilege_escalation,
exfiltration. Для verified malicious нужен хотя бы один обоснованный тег в области
задачи. Для benign теги угроз пусты. Неизвестный тип или спорная область задачи
требуют проверки или явного исключения, а не придуманного класса.

`representation_tags` описывают представление: comments, hex_literal,
char_function, url_encoding, string_concatenation. Они допустимы в обоих классах
и не являются доказательством злого умысла. Значение тега не обязано означать
обфускацию: обычный комментарий и строковая функция могут быть штатными.

`exfiltration_channels` уточняет механизм: file_export, external_transfer,
unauthorized_read, unknown. Последний означает подтверждённый тип угрозы при
неустановленном механизме. unauthorized_read требует достоверного основания
недопустимости чтения чувствительных ресурсов в текущем контексте.

`execution.outcome`: unknown / succeeded / failed / not_executed. Положительный
класс включает подтверждённые попытки, даже заблокированные СУБД. Код ошибки
сам по себе не доказывает атаку. Учебные примеры SQL не исполняются и имеют
`not_executed`; ожидаемый отказ нельзя записывать как реально наблюдавшийся failed.

## Отбор и защита от утечек

В основной корпус входят только purpose=research, full_sql и verified.
Фрагменты, обычный пользовательский текст и неизвестные единицы сохраняются
для аудита и отдельных экспериментов. Неудача SQL-парсера не устанавливает
unit_kind=non_sql: атакующий полный запрос может быть синтаксически ошибочным.

`detector_input(record)` возвращает только `sql`. Режим `include_context=True`
добавляет для пяти полей только `availability` и `value`. Вход нельзя получать
сериализацией всей записи. Из value политики дополнительно убираются
policy_id и version: модель получает правила, а идентификаторы остаются в учёте.
Исходные метки, теги, основания разметки, исходные ID,
типы генераторов, группы, результат выполнения и ссылки на свидетельства скрыты.
Передача SQL и контекста не освобождает от проверки prompt injection на этапе 9.

Для первого строгого парного сравнения SQL / SQL+context используется полный
набор пяти known-полей на одних и тех же ID. Подмножества с частичным контекстом
допускают отдельный заранее зафиксированный протокол и отдельные показатели.
Полный контекст не требует полного списка всех прав всей БД: частичная область
может быть достаточной для конкретного решения, если её достаточность обоснована.

Действия в permissions и policy — исследовательские категории, а не утверждение
об одинаковых именах привилегий во всех СУБД. Например, export не является
универсальным названием SQL-привилегии. Перевод исходных прав в эти категории
обосновывается источником и диалектом; при невозможности перевода сведения
сохраняются как неизвестные. Исполнение правил и разрешение противоречий между
ними потребуют отдельной реализации на этапе 8.

В отчёте доступности сохраняются known/unknown/not_applicable по каждому полю
и источнику. Нельзя улучшать показатели SQL+context простым исключением сложных
строк без такого же исключения в SQL-only. Размеры когорт и причины исключения
должны быть видны рядом с метриками.

## Текущий CSV

Поля query, label, source, label_name не содержат проверенных ролей, прав,
операций, политик или отдельного поля диалекта. Имена source с названием СУБД
могут стать предметом аудита, но не являются уже проверенным контекстом.
На этапе 3 исходные метки импортируются отдельно от целевых; первичный статус
переносимых аннотаций — needs_review до предусмотренного аудита этапа 4.
Исходные файлы и результаты этапа 1 не переразмечаются на этом этапе.

## Проверка

```powershell
python -B src/data_contract.py validate tests/fixtures/contract_examples.json
python -B src/data_contract.py audit-legacy data/processed/dataset.csv --output results/stage2/legacy_context_audit.json
python -B -m unittest discover -s tests -v
```

В учебных примерах `contract-fixture:obs-NNN/context/field` ссылается на поле
контекста записи с соответствующим observation_id в JSON-файле примеров.
Проверка структуры не исполняет SQL и не проверяет истинность деклараций.
Результат аудита старого CSV отражает отсутствие проверенных полей контекста,
а не устанавливает новые бинарные метки.
