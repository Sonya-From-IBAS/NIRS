Диалекты: MySQL, PostgreSQL, MSSQL и Oracle. На каждый блок и диалект приходятся 50 атак и 50 штатных примеров. Новые SQLi-сценарии в эту партию не входят. Существующие исходные корпуса сохраняются для прежних и последующих сравнений.

## Устройство корпуса

800 базовых строк составляют 400 пар. Обфусцированные 400 строк — связанные варианты половины базовых строк: по 200 из privilege и exfiltration, в каждом случае по 100 атак и 100 штатных запросов. Они имеют ссылки на родителей.

Целевая метка бинарная. Обфускация имеет отдельный блок генерации и теги представления. У штатного примера эталонный тег угрозы пуст; тематическую принадлежность показывает сценарий. Положительных примеров с тегом privilege_escalation — 300, с exfiltration — 300, включая обфусцированные варианты. Эти теги и блоки не являются взаимоисключающими классами.

Пять предметных областей: commerce, support, finance, research, operations. Одни и те же ресурсы, действующая роль и получатели встречаются в обоих классах. В соседних версиях сценария меняется область допустимого действия; роль и имена не кодируют ответ.

Шаблоны и сценарии предложены AI в текущей рабочей сессии. Корпус разворачивается детерминированной программой. В происхождении сохранены авторство, версия генератора и ссылка на неизменяемый каталог. Версия внешней модели не выдумывается: поле model остаётся пустым. Исследование рассматривает этот набор как контролируемые сценарии.

Версия авторского задания — stage5-controlled-renderers-v1. Его условия зафиксированы в generation_plan_v2 и этом протоколе: согласованные квоты, сценарная разметка, четыре диалекта, связанные преобразования и общий способ статического контроля.

## Паспорт и основание метки

До формирования конкретного SQL определяются схема и типы, искусственные данные, роль, технические права, операция приложения, получатель результата и полная политика в заданной области. Для процедуры дополнительно описаны исходный код и действие над полномочиями. Доверенный контекст доступен до решения детектора.

| Направление | Семейства |
|---|---|
| Повышение привилегий | Область объектов при выдаче прав; получатель; членство в роли; дальнейшее делегирование; процедура с явно заданным действием над правами |
| Эксфильтрация | Столбцы; строки/арендаторы; связанные ресурсы JOIN/EXISTS; раскрытие защищённого показателя через агрегат; назначение прикладного CSV-экспорта |

На семейство и диалект приходится десять пар. Для пяти пар из десяти также формируются варианты обфускации. SQL использует обычные SELECT, CTE, производные таблицы, JOIN, EXISTS, агрегаты, GRANT, членство в ролях и вызовы процедур. Стиль и сложность одинаково представлены в обоих классах.

Сначала отдельно задаются разрешённая и запрещённая области. Затем статический проверяющий извлекает действие из готового SQL и сопоставляет его с явным правилом. Запрошенный класс, имя файла, блок генерации и происхождение в вычислении метки не участвуют. Неизвестная конструкция, отсутствие подходящего правила и конфликт правил приводят к ошибке проверки, а не к назначению legit.

Например, технически доступный GRANT может выходить за разрешённую операцию приложения. Штатный запрос выдаёт права одобренному получателю на одобренный объект; нарушающий запрос затрагивает явно запрещённую область. Чтение чувствительного столбца получает exfiltration только при заданном запрете. Комментарий, название таблицы и наличие агрегации сами по себе класс не задают.

Политики представлены правилами allow/deny с JSON-условиями в стандартном поле condition. Условия сопоставляют конкретные ресурсы, полномочия, получателя, возможность дальнейшего делегирования, выбранный столбец, tenant, агрегат и назначение экспорта. Технические права и ограничения операции приложения хранятся отдельно.

## Контроль SQL и обфускации

Генератор: [generate_scenarios.py](../src/generate_scenarios.py). Проверяющий: [scenario_sql.py](../src/scenario_sql.py). Используется ограниченный набор разобранных конструкций для четырёх диалектов. Проверка различает объектные GRANT, членство в ролях, вызовы процедур и поддерживаемые формы SELECT. Для процедуры действие над правами извлекается из её исходного кода и сверяется с паспортом.

Применены три способа обфускации:

- комментарии между токенами с изменением регистра ключевых слов;
- составление фиксированной строки динамического SQL для поддерживаемых операций;
- символьное составление числовых констант вместе с комментариями.

Для каждого варианта восстанавливается каноническая исходная операция. Проверяются совпадение с родителем, одинаковый контекст, целевая метка и общая группа. Обработчик фиксированных строк принимает только заданные литералы и операторы конкатенации. Произвольные выражения и исполняемые комментарии не интерпретируются как обычные комментарии.

Диалектные конструкции сверены с документацией: [PostgreSQL GRANT](https://www.postgresql.org/docs/17/sql-grant.html), [PostgreSQL DO](https://www.postgresql.org/docs/17/sql-do.html), [MySQL GRANT](https://dev.mysql.com/doc/refman/8.4/en/grant.html), [комментарии MySQL](https://dev.mysql.com/doc/refman/8.4/en/comments.html), [SQL Server GRANT](https://learn.microsoft.com/en-us/sql/t-sql/statements/grant-object-permissions-transact-sql?view=sql-server-ver16), [SQL Server ALTER ROLE](https://learn.microsoft.com/en-us/sql/t-sql/statements/alter-role-transact-sql?view=sql-server-ver16), [Oracle GRANT](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/GRANT.html), [Oracle Dynamic SQL](https://docs.oracle.com/en/database/oracle/oracle-database/26/lnpls/native-dynamic-sql.html).

В этой партии представлены комментарии, символьные функции и конкатенация. URL-кодирование и hex не добавляются ради заполнения перечня тегов.

## Каналы эксфильтрации

Подтверждённое сценарной политикой запрещённое чтение входит в область задачи по ранее согласованному решению и получает unauthorized_read.

В семействе экспорта задан прикладной обработчик export_rows_v1: результат SQL сериализуется в CSV по пути из запроса операции. Получатель известен до классификации. Политика явно разрешает один маршрут и запрещает другой; оба маршрута имеют нейтральные имена. Тег file_export отражает этот объявленный прикладной механизм. SQL внутри такого сценария может совпадать, а контекст назначения различается.

Наличие внешней сетевой передачи в этой партии не заявляется. Названия таблиц и чтение системного каталога не используются как самостоятельное свидетельство эксфильтрации.

## Группы и контекстная оценка

Набор содержит 1 200 различных входов SQL+context и 686 различных текстов SQL. В 58 группах одинакового SQL встречаются обе метки при разном контексте; они охватывают 296 наблюдений. Такие случаи выделены в отдельный срез. Метрики SQL-only и SQL+context должны показываться раздельно: одинаковый текст не позволяет восстановить различающиеся контекстные решения.

Повторы между диалектами и сценариями сохраняются вместе с происхождением. Копии одного SQL с одним и тем же входным контекстом не имеют конфликтующих меток.

Для разбиений заданы десять семейных групп. Общие шаблоны объединяют их в семь связанных компонент; состав сохранён в [group_links.json](../results/stage5/group_links.json) и таблицах групп БД. Пары, родители, преобразования, переименования и производные между диалектами остаются связанными. Число строк, сценарных пар, текстов SQL и групп приводится отдельно; варианты не объявляются самостоятельными независимыми кампаниями. На этапе 6 эти связи учитываются при формировании разбиений и выборе числа фолдов.
